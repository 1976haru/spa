Why this hardening is required
Independent review of the Phase A implementation found one remaining safety gap:

ShopifyThemeCLI.capability_status() runs:
  shopify theme list --store <domain> --json

but currently:
- does not prove that the requested theme_id actually exists in that store,
- does not parse and persist the target theme's actual role/status,
- can report READY even if the requested theme ID is wrong,
- write_file() relies on caller-supplied request.target_is_live to decide whether --allow-live is required.

For a production safety boundary, the backend itself must know whether the exact target theme is the MAIN/live theme.
A caller must not be able to accidentally label a live theme as non-live and weaken the gate.

Shopify CLI officially supports theme list filtering by ID and reports theme IDs/statuses.
Use that capability or equivalent robust JSON parsing.
No live write in this task.

Mission
Harden target theme identity and actual role detection before this backend is merged to main.

======================================================================
1. TARGET THEME IDENTITY MUST BE VERIFIED
======================================================================

Refactor capability_status(store_id, theme_id=...) to verify the exact target theme.

Preferred command shape:
shopify theme list
  --store <domain>
  --id <numeric-theme-id>
  --json

If --id is not supported by the detected CLI version, fall back to:
theme list --store <domain> --json
and filter JSON locally.

Requirements:
- parse JSON only
- exact numeric theme ID match
- no fuzzy theme-name matching
- no assumption that an authenticated store implies the theme ID exists

New statuses/reason codes as appropriate:
THEME_ID_NOT_FOUND
THEME_ID_AMBIGUOUS
THEME_ROLE_UNKNOWN
THEME_LIST_INVALID_JSON

READY requires:
- CLI supported
- Theme Access credential present
- configured store matches
- exact theme ID found
- role/status reliably known

======================================================================
2. NORMALIZE SHOPIFY CLI THEME LIST JSON SAFELY
======================================================================

The CLI JSON shape can vary by CLI release.
Create a bounded parser helper that accepts plausible shapes such as:
- top-level list
- {"themes": [...]}
- other explicitly observed wrapper object

Do NOT recursively scan arbitrary nested data with fuzzy matching.

Normalize each theme to:
{
  "id": "<numeric>",
  "name": "...",
  "role": "main|unpublished|development|demo|unknown"
}

Accept common role/status field names only if explicitly mapped.
Normalize:
main/live/published => MAIN
unpublished => UNPUBLISHED
development => DEVELOPMENT
demo => DEMO

Unknown role => THEME_ROLE_UNKNOWN, not READY.

Do not include credential/token in parser diagnostics.

======================================================================
3. BACKEND-DERIVED LIVE STATUS
======================================================================

ThemeBackendCapabilities.details must include:
- verified_theme_id
- verified_theme_name when available
- verified_theme_role
- target_is_live = true/false
- identity_verified = true

The write backend must derive live status from this verified capability.
Do not trust request.target_is_live by itself.

Rules:
- actual role MAIN => actual_live = True
- all other verified roles => actual_live = False

If request.target_is_live disagrees with actual role:
return PRECONDITION_FAILED
reason_code = TARGET_ROLE_MISMATCH

======================================================================
4. LIVE WRITE GATE MUST USE VERIFIED ROLE
======================================================================

For actual MAIN/live target:
write_file() must require BOTH:
- confirmed=True
- allow_live=True

Only then add:
--allow-live

Even if request.target_is_live=False, if verified role is MAIN:
- reject as TARGET_ROLE_MISMATCH or ALLOW_LIVE_REQUIRED
- never push

For actual non-live target:
- do not append --allow-live
- if request.target_is_live=True, reject TARGET_ROLE_MISMATCH rather than silently accepting inconsistent state

Apply same verified-role logic to rollback_file().

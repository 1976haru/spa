Why this review fix is required before safe merge
The new post-write diagnosis/adoption feature is directionally correct and tests pass, but code review found TWO real production-safety gaps that matter specifically for the already-failed Store 001 apply:

1. RESTART RECOVERY GAP
- The real failed apply already created a durable homepage_featured_theme_backups row with status VERIFY_FAILED.
- But UI state fields such as:
  state["backup_id"]
  state["featured_last_apply_result"]
  state["featured_postwrite_diagnosis"]
  are in-memory.
- To run the newly added diagnosis code, ShopSource must be restarted on the new main after merge.
- On restart, backup_id / last apply UI state may be lost.
- Without durable hydration, Guided Flow can fall back to preflight/apply instead of offering diagnosis of the EXISTING failed write attempt.
- We must recover the latest post-write backup from DB by store+plan, without a second Shopify write.

2. ADOPTION TOCTOU GAP
- adopt_verified_remote(backup_id, diagnosis, confirmed=True) currently trusts the diagnosis dict captured earlier.
- A merchant/theme process could modify MAIN after diagnosis but before user clicks "검증 상태 확정".
- The method then updates local DB to REMOTE_JSON_VERIFIED without re-reading current remote.
- This can falsely mark a stale diagnosis as verified.
- Adoption must re-read/re-diagnose immediately at confirmation time and only update local state if CURRENT remote still qualifies.
- No Shopify write is needed; a fresh read-only check is sufficient.

Mission
Fix both gaps in the SAME branch, add restart/TOCTOU regression tests, rerun the full suite, commit/push.
Do not split into another micro-hotfix.
Do not merge main yet.

2. RESTART HYDRATION IN FEATURED UI
======================================================================

When rendering/resolving Featured for a READY plan after app restart:

If in-memory state has no current backup_id / last apply result:
- query latest_post_write_backup(current_store, current plan_id)

If latest backup status == VERIFY_FAILED:
hydrate:
- state["backup_id"] = backup_id
- state["featured_last_apply_plan_id"] = plan_id
- state["featured_apply_status"] = "VERIFY_FAILED"
- state["featured_last_apply_status"] = "VERIFY_FAILED"
- state["featured_last_apply_result"] = {
    "status": "VERIFY_FAILED",
    "reason_code": "POST_WRITE_DIAGNOSIS_REQUIRED",
    "backend_name": ...,
    "backend_reason_code": ...,
    "backup_id": ...,
    "write_performed": True,
    "reason": "이전 적용 시도 결과를 읽기 전용으로 확인해야 합니다."
  }

Do NOT invent the exact post-write mismatch code from the old row.
The old row only knows VERIFY_FAILED + backend selection reason.
Use a neutral durable reason:
POST_WRITE_DIAGNOSIS_REQUIRED

Guided Flow should route:
step 5 -> DIAGNOSE_POST_WRITE
label:
"5단계 · 이전 적용 결과 읽기 전용 진단"

Do NOT force the user back through:
1 -> 2 -> 3 -> 4 -> second apply
if the durable plan/backup already proves a prior write attempt that needs diagnosis.

If latest backup is already REMOTE_JSON_VERIFIED and plan has remote_json_verified=1:
hydrate enough state to route directly to step 6.

Do not overwrite newer in-memory state with an older durable backup.

4. TOCTOU-SAFE ADOPTION
======================================================================

Refactor adopt_verified_remote so it NEVER relies only on the UI-provided diagnosis dict.

Preferred signature:

adopt_verified_remote(
    backup_id,
    diagnosis=None,
    *,
    confirmed=False,
    backend_coordinator=None,
    client=None,
) -> dict

At adoption time:

1. require confirmed=True
2. lookup backup row
3. perform a FRESH diagnose_post_write(backup_id, same backend/client)
4. require current fresh diagnosis reason_code in:
   - POST_WRITE_VERIFIED
   - POST_WRITE_RAW_ONLY_NORMALIZED
5. require fresh:
   semantic_equal=True
   product_ids_match=True
   unrelated_sections_unchanged=True
   prefix_equal=True
   suffix_equal=True
   exact MAIN identity verified
6. require fresh expected_proposed_raw_hash == backup proposed_raw_hash
7. if a previous diagnosis dict was supplied, require its immutable identity fields to match:
   backup_id
   expected_proposed_raw_hash
   but do NOT trust its booleans over the fresh diagnosis
8. only then update backup/plan local DB state

If remote changed after the first diagnosis:
return:
status = ADOPTION_REFUSED
reason_code = fresh diagnosis exact code
write_performed=False

No Shopify write.
No rollback.

The audit JSON written on adoption must contain the FRESH diagnosis, not stale UI data.

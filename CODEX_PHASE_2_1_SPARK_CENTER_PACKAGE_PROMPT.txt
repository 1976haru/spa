1. 사용자 운영 조건 — 매우 중요
==================================================

사용자가 Spark Center 측에 직접 문의했고 다음 답변을 받았다.

- 상품 소싱은 사용자가 직접 해도 된다.
- 소싱한 파일/폴더를 Spark Center에 올리는 방식으로 운영할 수 있다.
- 따라서 C:\Users\...\AppData\Roaming\spark\storage\datasets 같은 Spark 데스크톱 내부 폴더에 굳이 생성할 필요가 없다.
- 프로젝트 로컬 작업폴더에서 업로드용 폴더를 만들고, 그 폴더를 Spark Center에 업로드하는 방식으로 운영한다.

이 사실을 이번 Phase의 기본 운영 전제로 사용한다.

다만 다음 두 사실은 구분한다.

A. Spark Center가 외부 소싱 파일/폴더 업로드를 허용한다고 지원 측에서 확인됨
B. 현재 ShopSource Studio가 생성하는 JSON package가 Spark Center 포털에서 실제로 성공 업로드되는지는 아직 수동 round-trip 미검증

따라서:
- manual folder upload workflow는 구현한다.
- 그러나 capability를 END_TO_END_VERIFIED 또는 PORTAL_UPLOAD_VERIFIED라고 표시하면 안 된다.
- 실제 포털 테스트 전에는 portal_package_verified = false를 유지한다.

==================================================
2. Phase 2.1 목표
==================================================

현재 Phase 2의 SparkHandoffConnector를 기반으로
100~200개 Store 운영에 적합한 "Spark Center 업로드 패키지 관리 흐름"을 구현한다.

사용자 입장에서 원하는 흐름:

Store 선택
→ 상태 선택
→ 상품 수 입력
→ [Spark Center 업로드 폴더 만들기]
→ 프로젝트 로컬 exports 아래에 업로드용 폴더 자동 생성
→ Validation PASS
→ [폴더 열기]
→ 사용자가 그 폴더를 Spark Center에 수동 업로드
→ 나중에 [업로드 완료 표시]

이번 Phase는 네트워크/API 자동 업로드가 아니다.
"업로드할 준비가 끝난 폴더를 정확하고 안전하게 만드는 것"이 목표다.

5. 새 서비스/Connector 설계
==================================================

권장:

SparkCenterPackageService
또는
SparkCenterPackageConnector

를 새로 둔다.

단, 기존 src/shopsource/connectors/spark_center.py의 CONTRACT_PENDING API connector와 개념이 섞이지 않게 주의한다.

현재 spark_center.py가 "서버/API connector" 의미라면:

- 기존 SparkCenterConnector = 공식 API/직접 연결, CONTRACT_PENDING 유지
- 새 SparkCenterPackageService = 수동 업로드 package 생성

처럼 분리한다.

이름만 봐도 혼동되지 않아야 한다.

새 서비스는 내부적으로 SparkHandoffConnector 또는 공통 dataset export core를 호출하여
동일한 상품 JSON을 생성한다.

중복 로직 금지.

==================================================
15. Validation
==================================================

기존 Spark handoff validation을 재사용한다.

추가 체크:

- upload folder에는 *.json 상품파일만 존재
- manifest/report는 upload folder 밖
- JSON 수 == product_count
- filename contiguous
- duplicate ASIN 없음
- sensitive field 없음
- INTERNAL_FIELDS 없음
- request_queues 없음
- key_value_stores 없음
- runtime/session file 없음
- package folder가 store ready directory 아래에 있음
- path traversal 없음

Validation FAIL이면 package_status를 CREATED로 기록하면 안 된다.
가능하면 FAILED로 기록하거나 export 자체를 실패시켜라.

2. 현재 코드의 구조적 취약점
==================================================

현재 자동 상세 캡처는 URL fragment marker에 의존한다.

background.js:

target.hash = shopsource_capture=<runId>
chrome.tabs.create(...)

content_product.js:

const marker = new URLSearchParams(location.hash.slice(1)).get('shopsource_capture')

if (marker) {
  waitForProductReadiness(...)
  submit(true)
}

문제:
Amazon redirect/navigation/history 과정에서 fragment가 사라지거나,
content script가 최종 product document에서 marker를 받지 못하면
탭은 열렸지만 auto capture가 시작되지 않는다.

현재 실제 사용자 현상이 정확히:
탭은 열림
DETAIL_OPENED 기록됨
DETAIL_COMPLETE 없음

이므로 URL fragment를 유일한 auto-capture trigger로 사용하면 안 된다.

==================================================
3. 해결 원칙
==================================================

Background Service Worker가 이미 알고 있는:

- runId
- expected ASIN
- opened tabId

를 source of truth로 사용한다.

즉:

ShopSource reserve next item
→ background chrome.tabs.create
→ background가 tabId + runId + asin 추적
→ 최종 Amazon product tab load complete
→ background가 content script에 명시적 메시지 전송
→ content script가 runId + expectedAsin으로 자동 상세 캡처
→ bridge 저장
→ DETAIL_COMPLETE
→ MASTER
→ background가 다음 item open

URL fragment는 fallback/debug용으로만 남겨도 되지만
자동 처리 성공 여부가 fragment에 의존하면 안 된다.

==================================================
4. Background → Content Script 명시적 handshake
==================================================

새 message type:

shopsource-batch-auto-capture

payload:

{
  type: "shopsource-batch-auto-capture",
  runId: "...",
  expectedAsin: "B0..."
}

background.js는 pending tab의 load complete를 감지한 뒤
chrome.tabs.sendMessage(tabId, message)를 호출한다.

content_product.js는 이 message를 받으면:

1. Amazon product page인지 확인
2. CAPTCHA 확인
3. waitForProductReadiness()
4. captureDetail()
5. 실제 ASIN과 expectedAsin 비교
6. batch_run_id = runId로 submit
7. success response 반환

==================================================
5. sendMessage race 방어
==================================================

tabs.onUpdated status=complete 시점에도
content script listener 준비가 아주 약간 늦을 수 있다.

background helper 권장:

async function triggerAutoCapture(tabId, runId, asin)

- 최대 10회
- 500ms 간격
- chrome.tabs.sendMessage
- "Receiving end does not exist"면 bounded retry
- success 응답을 받으면 종료
- CAPTCHA면 pause
- 그 외 명시적 capture error면 DETAIL_CAPTURE_FAILED
- 무한 retry 금지

총 handshake retry window는 약 5초 내외.

기존 45초 overall timeout은 마지막 safety net으로 유지.

==================================================
6. content_product.js submit 구조 개선
==================================================

현재 submit(auto=false)는 module-level marker를 사용한다.

다음처럼 explicit context를 받을 수 있게 변경:

async function submit({
  auto = false,
  batchRunId = null,
  expectedAsin = null
} = {})

또는 동등 구조.

detail payload:

{
  product,
  batch_run_id: batchRunId || marker || undefined
}

expectedAsin이 있으면:
captureDetail().asin과 정확히 일치해야 한다.

불일치:
throw Error("Opened product ASIN did not match queued ASIN")

server-side ASIN mismatch defense도 그대로 유지.

==================================================
7. 기존 fragment 자동실행과 중복 방지
==================================================

background handshake를 primary로 만들되,
기존 fragment fallback을 완전히 제거할 필요는 없다.

하지만 같은 페이지에서:

- fragment auto start
- background message auto start

가 동시에 실행되면 안 된다.

content_product.js에 page-level one-shot guard:

let autoCapturePromise = null

function runAutoCapture(context) {
  if (autoCapturePromise) return autoCapturePromise
  autoCapturePromise = ...
  return autoCapturePromise
}

fragment path와 message path 둘 다 이 함수 사용.

따라서 동일 상품 상세 capture는 1회만 실행.

==================================================
8. Pending tab 상태를 service worker restart에도 견디게
==================================================

현재 pendingTabs = new Map()은
Manifest V3 service worker가 suspend/restart되면 사라질 수 있다.

이것은 수백개 batch에서 불안정하다.

chrome.storage.session을 사용해 pending tab metadata를 보조 저장.

저장:

runId
tabId
asin
createdAt

절대 저장하지 말 것:
cookie
Amazon session
auth
page content
user account data

helper 예:

savePending(runId, record)
getPendingByTab(tabId)
clearPending(runId)

in-memory Map + chrome.storage.session 병행 가능.

extension restart 후에도 현재 browser session 동안 pending state 복구 가능.

==================================================
9. tabs.onUpdated 동작
==================================================

현재 onUpdated는 CAPTCHA만 검사한다.

수정:

pending tab이고:

A. CAPTCHA/robot page
→ clear pending
→ heartbeat CAPTCHA_DETECTED

B. status == complete
→ final URL이 amazon.com인지 확인
→ triggerAutoCapture(tabId, runId, asin)

C. Amazon product path가 아닌 redirect/intermediate page
→ 바로 실패 처리하지 말고 다음 onUpdated를 기다림
→ 45초 timeout safety net 유지

12. 기존 DETAIL_OPENED stuck item 복구
==================================================

현재 실제 DB에는 첫 retry 후 DETAIL_OPENED item이 남을 수 있다.

사용자가 Hotfix 적용 후 45초 기다리도록 강요하지 마라.

새 explicit user action:

[현재 열린 상세 다시 시도]

또는 기존 [다음 처리]에 recovery 동작 통합.

권장 service method:

recover_open_item(run_id)

조건:
- Batch RUNNING
- DETAIL_OPENED exactly 1

사용자가 명시적으로 클릭했을 때만:
- 해당 item → DETAIL_PENDING
- last_error = "Operator requested open-item recovery"
- checkpoint next_open_after reset
- event OPEN_ITEM_RECOVERED
- kickoff()으로 동일 상품 canonical URL 다시 open

자동 polling에서 reset 금지.
중복 탭 위험 때문에 user gesture에서만 사용.

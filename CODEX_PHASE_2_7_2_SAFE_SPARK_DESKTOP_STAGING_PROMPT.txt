==================================================
0. 핵심 결론
==================================================

Phase 2.7.1에서 Spark Desktop v1.0.3의 실제 loader contract를 확인했다.

중요:

Spark의 [데이터 불러오기] 폴더 선택은
선택한 외부 폴더의 JSON을 import/copy하는 기능이 아니다.

동작은:

1. 폴더 선택
2. 선택 경로에서 basename만 storageId로 취득
3. 실제 상품은 Spark 자체 storage root:

C:\Users\user\AppData\Roaming\spark\storage\datasets\<storageId>

에서 조회

4. 해당 내부 dataset 폴더가 없으면 0개

따라서 지금까지 D:\shop\...\exports\spark_center\...\ready\<package_id>
를 직접 선택해 0개가 나온 것은 JSON schema가 아니라 경로 계약 문제였다.

이번 Phase 목표는 Spark 앱을 수정하지 않고,
ShopSource가 생성한 상품 JSON 5개를
Spark의 observed dataset storage contract에 "안전하게 staging"하는 공식 사용자 동작을 만든다.

6. 허용되는 Spark storage 쓰기 범위
==================================================

이번 Phase에서는 명시적으로 다음만 허용한다:

%APPDATA%\spark\storage\datasets\<NEW_DATASET_ID>\

라는 "새 폴더 생성 + 상품 JSON 복사".

절대 수정 금지:

- 기존 Spark dataset 폴더
- 기존 Spark 소싱 job
- request_queues
- key_value_stores
- SDK_SESSION_POOL_STATE
- cookies
- tokens
- Spark app files
- Spark executable
- app.asar
- Spark DB가 있다면 그 DB

즉 기존 Spark 데이터를 건드리지 않고
새 dataset folder 하나만 추가한다.

==================================================
8. Atomic staging
==================================================

복사 도중 Spark가 반쪽 dataset을 읽지 않도록 atomic staging 사용.

Spark datasets root 아래에:

.shopsource_stage_<dataset_id>_<nonce>

임시 폴더 생성

→ JSON 5개 copy
→ 파일명/JSON parse/개수 검증
→ fsync 가능한 범위 수행
→ 최종:

<dataset_id>

로 rename/move.

실패 시 temp folder 정리.

기존 dataset은 절대 삭제하지 않는다.

==================================================

Source ready/*.json
→ Destination *.json

byte-for-byte copy.

각 파일 source/destination SHA-256 비교.

staging report:

file_count
source_hashes
destination_hashes
all_hashes_match

기록.

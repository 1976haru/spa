1. 이미 실제로 검증된 Spark 계약
==================================================

다음은 추측이 아니라 실제 사용자 PC에서 검증된 사실이다.

Spark manual data import:
- Windows 폴더 선택 UI가 열린다.
- 기본 위치는
  C:\Users\user\AppData\Roaming\spark\storage\datasets
- 입력 단위는 개별 JSON 파일이 아니라 datasets/<job_id> 폴더다.

실제 테스트:
- TEST_5ITEMS_20260929_192255 폴더를 생성
- 폴더 내부에 상품 JSON 5개만 저장
- 파일명:
  000000001.json
  000000002.json
  000000003.json
  000000004.json
  000000005.json
- request_queues 없음
- key_value_stores 없음
- Spark 데이터 불러오기에서 해당 폴더 선택
- 결과:
  전체 5개
  포함 5개
  제외 0개
- Spark UI에서 상품 이미지, ASIN, 상품명, 옵션 라벨, 브랜드가 정상 표시됨

따라서 이번 Phase에서는
datasets/<job_id> 폴더만 생성하는 Spark handoff를 구현할 수 있다.

그러나 아직 Shopify 실제 업로드까지 검증되지 않았다.
따라서 capability를 FULLY_SUPPORTED 또는 UPLOAD_VERIFIED 등으로 표시하면 안 된다.

권장 capability 상태명:
DATASET_LOAD_VERIFIED

또는 의미가 동일한 명확한 상태명을 사용하라.

==================================================
2. 이번 Phase 2의 목표
==================================================

MASTER DB에 이미 저장된 상품 중
현재 Store Profile에서 원하는 상태의 상품을 선택하여

Spark가 실제로 읽을 수 있는

datasets/<job_id>/
    000000001.json
    000000002.json
    ...

형태의 handoff 폴더를 자동 생성한다.

이 기능은 Amazon을 다시 크롤링하지 않는다.
MASTER DB의 원본 Spark payload를 재사용한다.

핵심 흐름:

Spark source
→ ShopSource MASTER DB
→ Store classify
→ PRIMARY / RESERVE / REVIEW ...
→ 선택 subset
→ Spark Dataset Handoff Folder
→ Spark 데이터 불러오기

==================================================
3. 가장 중요한 원칙
==================================================

1. 가격 때문에 MASTER 상품을 삭제하지 마라.
2. $35 상품도 MASTER DB에 보존한다.
3. export는 Store Decision의 final_status를 기준으로 한다.
4. manual override가 있으면 final_status를 그대로 존중한다.
5. 동일 ASIN은 하나의 handoff 폴더에 한 번만 내보낸다.
6. Spark 상품 JSON에는 ShopSource 전용 내부 필드를 삽입하지 마라.
7. 가능한 한 실제 Spark raw payload를 그대로 보존하여 내보낸다.
8. request_queues를 만들지 마라.
9. key_value_stores를 만들지 마라.
10. session cookie/token을 읽거나 내보내지 마라.
11. SDK_SESSION_POOL_STATE.json 또는 crawler runtime 파일을 생성하지 마라.
12. 기존 Spark 작업폴더를 수정하거나 덮어쓰지 마라.
13. 항상 새 job folder를 만든다.
14. 기존 folder가 있으면 명시적 overwrite 옵션 없이는 실패시켜라.
15. 실제 Shopify 업로드 API는 이번 Phase에서 구현하지 마라.

4. Raw Payload 선택 규칙
==================================================

현재 DB에는:
- products.raw_json
- product_occurrences.raw_json
이 존재한다.

Spark handoff에 사용할 payload는 다음 우선순위로 정한다.

1. 해당 product의 가장 최근 유효 product_occurrences.raw_json
2. 없으면 products.raw_json

"가장 최근" 기준은 가능한 경우:
- collected_at
- occurrence id
순으로 안정적으로 정한다.

payload가 JSON object가 아니거나,
필수 식별정보가 없으면 해당 상품은 무조건 조용히 누락하지 말고 validation error로 기록하라.

최소 필수:
- asin
- title

가능하면 기존 Spark payload의 다음 필드는 그대로 유지:
- url
- asin
- title
- brand
- price
- options
- quantity
- tags
- category
- overview
- aboutThis
- images
- rating
- reviewCount
- _sourceUrl
- _listPage
- _collectedAt

필드 값을 임의로 정규화하거나 재작성하지 마라.
이번 Phase는 "원본 payload 보존"이 우선이다.

5. SparkHandoffConnector 구현
==================================================

현재 src/shopsource/connectors/spark_handoff.py는
CONTRACT_PENDING으로 막혀 있다.

이를 실제 verified dataset folder handoff로 구현하라.

권장 API 예:

SparkHandoffConnector.export(
    store_id="001",
    statuses=["PRIMARY"],
    out_root=Path(...),
    limit=None,
    job_id=None,
    db=None,
)

정확한 signature는 기존 architecture에 맞게 조정 가능하다.

결과는 객체 또는 Path 하나로 끝내지 말고,
호출자가 다음을 알 수 있게 구조화된 result를 반환하는 것을 권장한다.

- job_id
- folder
- product_count
- asin_count
- statuses
- manifest_path
- validation_report_path
- warnings

기존 ExportConnector interface와 충돌한다면
최소 변경으로 확장하라.

6. Job ID / 폴더명 규칙
==================================================

사용자가 job_id를 지정하지 않으면
충돌 가능성이 낮고 사람이 읽을 수 있는 값을 생성하라.

예:
SS_001_20260929_193000_ab12

필수 조건:
- Windows 파일명 안전
- store_id 포함
- timestamp 포함
- 충돌 방지 suffix 가능
- 기존 폴더와 충돌하면 덮어쓰지 않음

사용자가 job_id를 지정한 경우에도
path traversal:
..
/
\
등을 이용해 out_root 밖으로 탈출할 수 없도록 검증하라.

==================================================
8. Status 선택
==================================================

기본값은 PRIMARY만 export하도록 한다.

CLI에서 복수 status를 허용하라.

예:

shopsource spark-handoff --store 001 --status PRIMARY

shopsource spark-handoff --store 001 --status PRIMARY --status RESERVE_A

RESTRICTED는 기본 export에 절대 포함하지 않는다.

사용자가 명시적으로 RESTRICTED를 요청할 경우에도
경고 또는 별도 allow flag를 요구하는 방향을 검토하라.

예:
--allow-restricted

단, 불필요하게 복잡하게 만들지 말고 안전한 기본값을 우선한다.

==================================================
9. limit / ASIN 선택
==================================================

테스트와 실제 운영을 위해 아래 기능을 지원하라.

- --limit N
- optional --asin ASIN (복수 가능)

예:

shopsource spark-handoff --store 001 --status PRIMARY --limit 5

또는:

shopsource spark-handoff --store 001 --asin B0XXXX --asin B0YYYY

ASIN 직접 지정 시에도 해당 Store에 decision이 존재해야 하는지,
아니면 MASTER에 존재하면 허용할지 명확히 정하고 문서화하라.

권장:
Store Decision이 존재하는 상품만 허용.
왜냐하면 Store별 판정을 통과한 상품을 handoff하는 것이 목적이기 때문이다.

11. Manifest / Validation Report
==================================================

중요:
Spark가 선택하는 job folder 안에는 상품 JSON만 넣어라.

즉 아래처럼 하지 마라.

job_folder/
  000000001.json
  manifest.json   <-- 금지

Spark가 manifest를 상품으로 읽을 위험이 있다.

Manifest와 validation report는 job folder 바깥에 둬라.

권장 구조:

exports/
  spark_handoff/
    jobs/
      <job_id>/
        000000001.json
        000000002.json
    manifests/
      <job_id>.manifest.json
    reports/
      <job_id>.validation.json

또는 architecture에 더 적합한 sibling 구조를 사용하라.

Manifest 최소:
- schema_version
- job_id
- store_id
- store_name
- created_at
- selected_statuses
- product_count
- asin_count
- asin_hash
- source_job_ids
- output_folder
- capability_status = DATASET_LOAD_VERIFIED
- shopify_upload_verified = false

Credential:
- AccessToken
- cookie
- session-token
- aws-waf-token
등은 절대 manifest에 넣지 마라.

==================================================
12. Validation
==================================================

export 완료 후 자동 validation을 수행하라.

최소 검증:

- job folder 존재
- JSON 파일 수
- 순차 filename
- 각 파일 JSON parse PASS
- asin 존재
- title 존재
- duplicate ASIN 없음
- product_count == file_count
- manifest asin_count 일치
- 내부 ShopSource field가 product JSON에 추가되지 않았는지
- credential/session 관련 key가 새로 추가되지 않았는지

가능하면 기존 probe_schema를 재사용하되,
Spark handoff validation에 필요한 별도 검증 layer가 있으면 최소 모듈로 분리한다.

validation 실패 시
"export 성공"으로 표시하지 마라.

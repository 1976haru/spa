2. 실제 코드 기반 1차 원인
==================================================

현재 browser_extension/shopsource_capture/content_search.js는
검색 카드에서 href가 존재하면 그대로 candidate.url로 저장한다.

현재 코드 패턴:

const href = ...
const match = href.match(...)
const url = href ? new URL(href, location.origin).href
                 : (match ? canonical : null)

Sponsored 카드의 href는 종종 실제 /dp/<ASIN> 직접 URL이 아니라
Amazon tracking/redirect URL일 수 있다.

그 결과 Batch가 tracking URL을 열고,
product content script의 다음 조건:

/\/(?:dp|gp\/product)\/[A-Z0-9]{10}/

을 만족하지 않거나,
redirect 과정에서 #shopsource_capture marker가 사라져
자동 상세 capture가 실행되지 않을 수 있다.

실제 테스트에서도:
- 직접 상품 후보 1개는 성공
- Sponsored 후보 4개는 모두 실패

라는 패턴이므로
이 가설을 우선 검증/수정한다.

단 원인을 단정하지 말고
현재 DB의 browser_batch_items.last_error / event log도 함께 확인한다.

==================================================
4. Canonical Amazon Product URL helper
==================================================

Python과 JS 양쪽에 ASIN 기반 canonical URL 원칙을 적용한다.

US marketplace 기준:

https://www.amazon.com/dp/<ASIN>

Python helper 권장:

def canonical_product_url(asin: str) -> str:
    validate ASIN
    return f"https://www.amazon.com/dp/{asin.upper()}"

위치는:
src/shopsource/capture/validation.py
또는 적절한 공용 모듈.

==================================================
5. Search capture URL 수정
==================================================

content_search.js에서 product.url은
검색 카드의 tracking href를 그대로 사용하지 않는다.

ASIN이 유효하면 기본 product.url은 반드시:

https://www.amazon.com/dp/ + asin

으로 저장한다.

원래 클릭 href가 필요하면
진단 metadata로만 별도 보존할 수 있으나,
Spark payload나 detail open URL로 사용하지 않는다.

검색 결과 source evidence는 이미:
_sourceUrl = search page URL
로 남으므로 tracking href 보존은 필수가 아니다.

==================================================
6. Server-side defense
==================================================

Extension만 믿지 말고
CaptureService.capture_search()에서도
accepted candidate의 url을 ASIN canonical URL로 정규화한다.

즉 과거/다른 client에서 tracking URL이 들어와도
DB의 search payload detail-open URL은 canonical로 저장.

단:
_sourceUrl은 실제 검색 페이지 URL 유지.

==================================================
7. 기존 DB 후보 복구
==================================================

이미 저장된 4개 후보는
search_payload_json에 tracking URL이 남아 있을 수 있다.

사용자가 다시 Amazon 검색 캡처를 할 필요가 없도록 한다.

BatchSourcingService.next_item()에서
detail open URL은 저장된 payload.url보다
item.asin을 기준으로 canonical_product_url(asin)을 우선 사용한다.

즉 기존 DB의 잘못된 URL도 자동 복구.

반환:

{
  "asin": "...",
  "url": "https://www.amazon.com/dp/<ASIN>",
  "batch_run_id": "..."
}

==================================================
8. FAILED 4개 재시도
==================================================

현재 실제 Batch는 DONE + FAILED 4 상태다.

"실패만 재시도" 클릭 시:
- FAILED 4개를 DETAIL_PENDING으로 reset
- retry_count=0
- status=RUNNING
- finished_at=NULL
- canonical URL로 첫 상품 다시 시작

되어야 한다.

DONE_WITH_ERRORS를 도입하면
RETRY 가능 상태로 유지.

기존 DONE run에서도 실패가 있으면 Retry 버튼이 동작해야 한다.

==================================================
9. DONE 상태 의미 수정
==================================================

현재 4개 실패가 있어도 Batch가 DONE으로 표시된다.

운영자에게 오해를 준다.

다음 상태 추가 권장:

DONE_WITH_ERRORS

조건:
pending == 0
failed > 0
target processing 종료

이면:

DONE_WITH_ERRORS

로 표시.

성공 완료:
DONE

CAPTCHA:
PAUSED_NEEDS_USER

UI:
DONE_WITH_ERRORS = 경고

"4개 실패 · 실패만 재시도 가능"

표시.

==================================================
10. Product page readiness
==================================================

현재 content_product.js auto capture는 marker 감지 후
setTimeout(..., 900) 한 번으로 실행한다.

실제 Amazon 페이지에서 DOM/JSON-LD가 늦게 준비될 수 있다.

자동 capture 전에 bounded readiness wait 추가.

예:
최대 10~15초
500ms 간격

ready 조건:
- #productTitle text 존재
OR
- Product JSON-LD name 존재

CAPTCHA가 나타나면 즉시 중단.

15초 내 ready 안 되면:
DETAIL_CAPTURE_FAILED
reason = "Product detail DOM did not become ready"

무한 대기 금지.

새 네트워크 요청 금지.

11. ASIN mismatch 방어
==================================================

FAILED 또는 RETRY

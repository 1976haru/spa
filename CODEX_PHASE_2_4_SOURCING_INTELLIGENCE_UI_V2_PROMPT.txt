==================================================
1. 이번 Phase의 목적
==================================================

현재 프로그램은 자동 소싱까지 동작하지만,
운영자가 100~200개 샵을 다루기에는 GUI가 너무 단순하고
각 Store에 어떤 Amazon 검색 주제어를 넣을지 사람이 직접 설계해야 한다.

이번 Phase의 목표는 두 가지다.

A. Store별 검색 주제어 추천/검증 시스템
B. 운영자용 현대적 UI V2

기존 backend / DB / classifier / Spark Center package는 유지한다.
기존 Tkinter UI도 fallback으로 유지한다.
새 UI는 별도 entry point로 만든다.

==================================================
7. Keyword 생성 단계
==================================================

Stage A — deterministic seed expansion

Store profile의 category/include keyword를 기반으로
문제/장소/용도 조합 생성.

예:
car + trunk + organizer
car + backseat + storage
center console + tray
seat gap + filler

단 특정 Cabin Tidy 문구를 core에 hardcode하지 말고
Store Profile 기반 generic template engine으로 구현.

Store별 seed template은 profile optional field로 확장 가능.

==================================================
8. Existing Product Text Mining
==================================================

MASTER/Keepa에서 확보한 상품 title과 category를 이용해
candidate n-gram을 추출한다.

1~4 gram 후보.

stopword:
the, and, for, with, of 등 일반어 제외.

브랜드명 과대표집 방지.

ASIN/숫자/사이즈 문자열 제거.

상품 0개일 때도 profile seed만으로 동작.

==================================================
9. KeyBERT
==================================================

KeyBERT를 optional intelligence dependency로 사용.

목적:
상품 title 묶음과 store description에서
의미 있는 keyword/keyphrase 추출.

KeyBERT가 설치되지 않은 환경에서는
deterministic ngram fallback으로 동작.

프로그램 전체가 시작 실패하면 안 된다.

==================================================
10. sentence-transformers
==================================================

optional dependency.

Store concept text embedding과
candidate keyword embedding cosine similarity로
semantic_fit 계산.

권장 모델:
가벼운 sentence-transformers 모델.

모델 이름은 설정 가능하게 하고,
첫 실행 시 큰 모델을 자동으로 강제 download하지 마라.

모델 미설치/오프라인이면
lexical scoring fallback.

==================================================
11. RapidFuzz
==================================================

RapidFuzz를 사용해:
- 거의 같은 keyword
- 단어 순서만 다른 keyword
- singular/plural 유사어

중복 제거.

예:
car trunk organizer
trunk organizer for car
car trunk storage organizer

를 완전히 동일하게 처리하지는 말되
유사도 threshold 기반 그룹으로 묶는다.

사용자가 대표 keyword를 선택 가능.

==================================================
12. Keepa로 Keyword Validation
==================================================

추천 keyword를 실제로 sourcing recipe에 추가하기 전에
Keepa Product Finder로 lightweight validation 가능하게 한다.

[검증] 버튼.

검증 항목:
- 후보 ASIN yield
- 가격대 적합 비율
- rating/review 조건 충족
- 위험상품 비율
- 이미 MASTER에 있는 ASIN 비율

Token 비용이 발생하므로:
- 검증 전 예상 token 안내
- 5~10 keyword씩 batch
- 사용자가 직접 실행
- 자동 전체 검증 금지

결과를 keyword score에 반영.

22. Keepa Python Client 검토
==================================================

현재 raw urllib KeepaProvider는 동작한다.

하지만 공개된 akaszynski/keepa Python client를 비교 검토한다.

장점:
- product_finder
- query
- AsyncKeepa
- ProductParams validation
- typed/Pydantic response 지원

Phase 2.4에서 즉시 전체 provider를 갈아엎지는 말고
adapter spike를 작성한다.

조건:
- 현재 tests와 token control 유지 가능
- API key redaction 유지
- query field validation 개선
- dependency 증가 비용 검토

결과가 좋으면 KeepaClientAdapter로 전환.
아니면 현재 provider 유지.

선택 이유를 문서화.

23. Data Layer
==================================================

SQLite는 transactional source of truth로 유지.

현재 단계에서 PostgreSQL migration 금지.

대규모 분석:
100k~millions product에서 병목이 확인되면
DuckDB 또는 Polars를 read-only analytics sidecar로 검토.

이번 Phase에서는
analytics adapter interface와 benchmark만 가능.

Real incident
- Store 001 Theme Access credential is stored and UI can use it.
- Theme Access CLI = READY.
- Featured plan = 4/4 READY.
- Featured preview = PREVIEW.
- Explicit MAIN live confirmation was given.
- Apply result shown in UI = CONFLICT.
- No backup row was created, so conflict happened before backup/write.
- External diagnosis worktree could not access Windows credentials and therefore could not determine the conflict reason.

Mission
Move the read-only preflight diagnosis INTO ShopSource itself, where the same runtime/user profile already has credential access.

The operator must be able to click one beginner-safe button and see the exact first failing gate BEFORE any write.

No Shopify mutation in this task.
No real live apply.
No rollback.
No credential creation/deletion.

======================================================================
1. EXTRACT SHARED READ-ONLY PREFLIGHT
======================================================================

Refactor FeaturedProductThemeApplyService so the pre-backup/pre-write guards are reusable in a read-only method.

Preferred API:

FeaturedProductThemeApplyService.preflight(
    plan_id,
    preview,
    *,
    store_id,
    backend_selection="AUTO",
    allow_live=False,
    backend_coordinator=None,
    client=None,
) -> dict

Requirements:
- MUST NOT create backup files
- MUST NOT insert backup DB rows
- MUST NOT call ThemeWriteBackendRouter.write()
- MUST NOT call themeFilesUpsert
- MUST NOT run shopify theme push
- MAY perform read-only backend capability/read_file operations
- return write_performed=False always

Refactor apply() to call the same shared preflight logic first so diagnostic and actual apply cannot drift.

Do not weaken any existing safety guard.

======================================================================
4. APPLY() MUST REUSE PREFLIGHT
======================================================================

Actual apply() flow should become conceptually:

1. preflight(...)
2. if preflight status != READY_TO_APPLY => return equivalent guarded result, no write
3. create exact backup
4. router write
5. same-backend post-read verify
6. REMOTE_JSON_VERIFIED or VERIFY_FAILED

Preserve:
- confirmed=True requirement
- allow_live=True requirement
- exact MAIN identity
- 4 ACTIVE products
- isolated diff
- commented JSON preservation
- exact product IDs
- no backend fallback after write attempt
- rollback behavior unchanged

Because apply() currently has many inline guards, refactor carefully and add regression tests.

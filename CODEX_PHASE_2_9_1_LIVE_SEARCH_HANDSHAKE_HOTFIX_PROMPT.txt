0. Actual live failure
==================================================

User started LIVE 2,000 campaign.

Observed:
- campaign status = RUNNING
- Amazon search worker tab opens
- after 15–20 seconds:
  unique_candidates = 0
  search_pages = 0
  detail_complete = 0

Therefore:
UI → local bridge → extension campaign command → background navigateCampaign()
is working at least enough to open the Amazon search tab.

But the first search page is not being successfully auto-captured / acknowledged.

Current code in content_search.js relies on:
location.hash contains shopsource_campaign
→ setTimeout(()=>submit(campaignId),1200)

This is fragile because Amazon navigation/redirect/canonicalization may drop/change the hash, content script timing may precede result readiness, or submit errors are suppressed for campaign mode.

We need an explicit search-page handshake similar to the existing detail worker handshake.

Do NOT cancel or recreate the user's current campaign.
The hotfix must allow the same persisted campaign ID to continue after extension/UI reload.

2. Required architecture change
==================================================

Do not rely on URL hash auto-submit as the primary trigger.

Background service worker must own search-campaign state and explicitly tell the Amazon content script:

{
  type: "shopsource-campaign-capture",
  campaignId: "<LC_...>"
}

after the search worker tab finishes loading.

Hash marker may remain only as fallback/debug/recovery marker.

Add storage.session persistence for campaign search workers, analogous to detail worker persistence.

shopsource.searchWorker.<campaignId>

Record:
campaignId
tabId

lastUrl
captureInFlight
lastCaptureAt

On service-worker restart:
restore valid search worker tab records.

Do not touch user-opened Amazon tabs.

==================================================
4. Explicit search handshake
==================================================

Add function, conceptually:

triggerCampaignSearchCapture(tabId, campaignId)

Behavior:
- wait until tab status complete
- send chrome.tabs.sendMessage:
  {type:"shopsource-campaign-capture", campaignId}
- retry receiver-not-ready several times (e.g. 10 × 500ms)
- content script itself performs result-readiness wait before capture
- one page must be captured once only
- no duplicate submit due both hash and background trigger

Use a per-campaign/page in-flight guard.

==================================================
5. Search result readiness
==================================================

content_search.js should not blindly capture at 1200ms.

Implement a bounded wait:
- look for visible valid search result cards:
  [data-component-type="s-search-result"][data-asin]
- OR detect CAPTCHA/robot-check
- OR timeout

Suggested:
poll every 500ms
max 20 seconds

If cards appear:
capture.

If CAPTCHA:
send shopsource-campaign-captcha.

If timeout:
return structured:
SEARCH_RESULTS_NOT_READY

No infinite loop.

==================================================
6. Auto trigger dedupe
==================================================

A page may receive:
- hash fallback

- user button click

Prevent duplicate campaign capture for the same campaign + normalized search URL + page.

Use content-script in-memory key and/or server-side idempotency if appropriate.

Do not prevent manual non-campaign capture.
